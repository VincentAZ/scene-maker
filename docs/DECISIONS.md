# Decisions for review

2026-10-28 — Initial implementation from the supplied creator-studio brief.

- Product name: Scene Maker. A warm, cinematic workspace with a slate shell, ivory canvas, and lime accent. Creator language is used throughout the workspace.
- This repository is a local-first application. The browser editor and a local Node service run together. Engine jobs run on the creator's machine; there is no public deployment or cloud account requirement.
- “Mixxar” is interpreted as Adobe Mixamo, pending correction. No undocumented Mixamo generation API is invented. User-owned FBX/GLB characters and animations can be imported, with Blender handling FBX conversion. The built-in library is original procedural content and does not redistribute Adobe's raw character library.
- The initial character art direction is stylized, fully weighted skeletal meshes, with masculine/feminine/mannequin variations and profession outfits. Photorealistic characters can be imported. “Fully skinned” means skeletal skin weights, not a promise of photographic realism.
- Technical settings require Studio settings → Connections. Each character's personality and creative direction are directly available; model and engine identifiers stay in Connections.
- Seven model providers are supported with user-supplied credentials and explicit model IDs: OpenAI, Anthropic, Google, xAI, Moonshot (Kimi), OpenRouter, and LM Studio (local; its server address takes the place of a key). No default model IDs are frozen into the app. Credentials remain in the local server's private data directory.
- Without credentials, a clearly labeled offline command helper handles a bounded set of scene operations. It never claims to be a live AI model. Live assistant instructions become validated scene commands; arbitrary generated code is never executed.
- Blender is a local command-line adapter. Unreal receives a portable animated GLB plus an editor import script. A live Unreal editor is required to verify its import on the creator's installation.
- Project persistence is on disk, with revision checks and atomic writes. Undo/redo is per open editing session. Exported project JSON carries the portable scene definition; ZIP packages also carry original imported assets and animated GLB.
- Create the GitHub repository as private by default, preserving the user's ability to choose a public release later.

## Implementation follow-through

- AI-generated character specifications are materialized by a trusted Blender Python adapter, with skinned GLB output. The adapter has a bounded procedural vocabulary; it does not pretend to produce arbitrary photorealistic geometry.
- Imported native animations remain associated with their originating asset. Generic procedural motion and arbitrary skeleton retargeting are distinct capabilities; the latter is not claimed complete.
- A Blender 4.5.3 LTS binary from download.blender.org was downloaded into ignored `.data/tools/blender` and connected for verification on this machine. It is not part of the source distribution; other machines install/configure Blender separately.
- Production packages are retained locally under `.data/exports` as well as offered for download, making generated outputs inspectable and recoverable.
- Provider calls were tested with deterministic AI SDK models because no API credentials were supplied. No credentials were copied from unrelated projects or browser accounts.
- The repository was created as private at `VincentAZ/scene-maker` using the signed-in GitHub UI. Existing SSH authentication is used for the push.

- Generated assets can carry up to 256 validated geometric parts (sphere, box, cylinder, cone, torus), with transforms, colors, and character bone bindings. Blender materializes custom characters; the preview builds custom props from the same declarative schema. This supports new shapes without executing generated code.

## Assistant workflow follow-through

- Assistant requests return ordered, schema-validated studio steps. Scene edits, new/copy/open/save, object selection, camera framing, playback, cast conversation, library search, exports, history, and tool navigation share a single executor. Credentials remain outside chat in Connections.
- A workflow stops on its first failed operation and reports the steps that completed. Its success response appears only after execution. Completed edits remain available for undo; exports and conversation requests are not silently retried.
- Project switches wait for a serialized save queue to drain, including edits made during an in-flight save. Opening a saved project verifies the revision used for planning. Reopening the current project retains its current content; revisiting an earlier project in the same workflow uses the revision saved by that workflow.
- The live planner receives up to 20 recent chat messages, project summaries, and up to three explicitly named saved project definitions. Snapshot caching binds validation to the same project data the planner saw. Undo/redo must be isolated from further plan steps because their resulting state belongs to the browser's session history.
- Exports wait for the requested scene and its imported assets to render, then bake animation against an isolated copy of the skeletons, geometry, and materials. Editing or switching scenes cannot mutate an export in progress.
- File imports remain an explicit local file-selection flow. The offline helper offers named project operations and a documented fixed command vocabulary; open-ended planning still requires a provider.

## Cast conversation follow-through

- A round means one turn per visible character. Continuing after a stopped or interrupted run starts with the character after the last completed speaker, preserving conversational order. Provider connections and available dialogue capacity are checked before paid calls; retries remain disabled to avoid repeating completed turns.
- The local conversation endpoint streams completed, validated turns as newline-delimited JSON. The browser applies each turn immediately and waits for its save before consuming the next streamed turn. Closing the request or pressing Stop aborts the active provider request and prevents later turns. The plain JSON endpoint behavior remains available, with partial scene data on an interrupted run.
- Conversation turns are placed sequentially after existing scene actions. Breathe clips fill the waiting time on the speaker's track. A text-length estimate sets the speaking action duration; creators can adjust it in Details. This is staged motion and caption timing, not generated voice or lip synchronization.
- Dialogue references its action by clip ID, so captions and subtitle timings follow action reorder/duration changes. Removing an action or character preserves its dialogue as untimed history. Existing projects with untimed dialogue still load unchanged.
- Transcript preview jumps to the selected line and plays its action. Timed SRT is available from the cast dialog, from the assistant, and inside production packages. Editing or switching scenes while models are working stops the conversation and retains delivered turns and the creator's newer edits.
- HTTP lifecycle and cancellation are verified with SDK mock models. The browser caption fixture is explicitly labeled authored dialogue and does not imply a paid/live model run. Completed delivered turns are saved through the normal revision-checked project queue; this does not promise recovery of an unfinished provider call after a process or network crash.

## Prop interaction follow-through

- Pick up, Take a sip, and Put down derive prop ownership from the entire timeline. No previous-frame state is required, so reverse scrubbing and export produce the same pose. Pick up holds across later actions; a standalone sip acquires and returns the prop within its own clip. Put down returns to the prop's authored starting transform.
- Arm contact uses analytic two-segment reach solving in world coordinates. Known hand/foot bones supply endpoints on imported rigs; compatible rigs without those bones use rest-length proportions. Low reaches add a crouch and preserve computed foot contact points. This is bounded choreography, not collision or general physical simulation.
- Reach is checked at both acquisition and release. A distant prop stays home. If the actor walks away before Put down, the held prop stays in hand and the preview explains how to correct the staging. Failed release prevents a later actor or second prop from taking over the occupied hand. The assistant receives that feedback and the current playhead.
- One right-hand prop per character is supported. Overlapping scheduled ownership is rejected during scene validation. A cast dialogue response that requests a sip while another character owns the only cup uses a talking gesture instead.
- Imported body animation and procedural poses use the same sampler for contact checks, preview, and baking. Carrying constrains the right arm without erasing the native motion on the rest of the body. This does not establish arbitrary skeleton retargeting.
- Custom prop definitions may include local `grip` and `mouth` points. The built-in cup supplies known defaults. Full hand/finger articulation, collision avoidance, automatic approach navigation, and arbitrary placement surfaces remain work to do.

## Imported humanoid follow-through

- Recognized humanoids get an anatomical pose adapter. It records the original bind transforms, establishes arms-down neutral orientations, and applies studio rotations in character space through the actual bone hierarchy. Original skin inverse matrices remain unchanged. Native clips use the original bind pose rather than this calibrated pose.
- Mapping accepts the studio names, common humanoid aliases, and namespaced Mixamo-style joints. Required ancestry is checked, and helper bones between recognized joints are preserved. Nonuniform or mirrored scale along the bone hierarchy is unsupported. Unrecognized characters keep native playback and receive a plain-language hint when studio actions are requested.
- Native translation is sampled from the original clip's start and end and accumulated across the sequence. Horizontal travel follows the hips; vertical travel follows the lowest mapped foot contact when available, avoiding a false height change from crouching alone. Original animation offsets are aligned to the character's scene position. Facing-direction carry-over and transition blending remain separate, unfinished work.
- Every character load owns its GLTF scene, so its original node identifiers are retained for native tracks targeting unnamed nodes. Export baking records animated ancestor/object transforms, bone transforms, scale, and morph weights. A bone-only bake was insufficient for FBX animation on the armature object.
- The verification fixture is generated locally with Blender and is not a downloaded or licensed Adobe asset. Chrome file upload was unavailable because the extension's file-URL permission is disabled, so this test used the same local import API, registered its result in an isolated project, and verified browser action editing, assistant direction, saving, and export from that project. No browser permission was changed.
- Native clips remain associated with their original asset. Automatic native-animation transfer across different skeletons and unconstrained rig matching are not claimed complete.

## Ladder choreography follow-through

- A targeted climb uses the ladder's authored position, facing, scale, and rung profile. It approaches in a straight line, mounts the first rungs, advances one hand or foot at a time, and settles into an upper-rung stance. The default duration is six seconds. The last climb holds its final contacts; a following action inherits its root position and heading.
- The built-in ladder defines seven rungs on a 2.5m frame. Custom assets may define `ladder` dimensions and rung spacing/count; this generates matching geometry unless explicit parts or an imported model supply it. Those supplied meshes require accurate metadata. The studio does not infer rungs from an arbitrary mesh.
- A pure timeline sampler drives approach, root movement, contact goals, preview, reverse scrubbing, and export. Native root travel now enters this sampler before the climb's approach is calculated. Four analytic limb solves place hands and feet using calibrated rig endpoints.
- Known unsupported rigs, hidden or animated ladders, unsuitable sizes, and mismatched base heights leave the character at its starting position with feedback. A rig whose proportions cannot reach a computed contact produces a reach warning. This is procedural choreography, not collision-aware navigation or physical simulation.
- Two climbers cannot overlap on the same ladder, including a final held stance. Climbing requires both hands free; a failed earlier put-down preserves the prop and reports the conflict. Creators must stage transitions and an exit path. Platform detection, stepping off, descent, finger articulation, collision avoidance, and general motion blending remain unfinished.
- The action library chooses the nearest visible ladder. The offline assistant prefers a named ladder, then the nearest one, and directs a character even if the prompt only names the ladder. Missing ladders produce an actionable message. Old untargeted climb clips retain their original generic motion for project compatibility.

## Authored routes follow-through

- Walking and running motions can carry a level route with 2–32 points. The first point is zero; subsequent points use local offsets relative to the character's position and facing at the start of that clip. Each coordinate is bounded to 50 local meters. Moving, scaling, rotating, or reordering the character's preceding actions carries the route with them.
- Smooth routes use an interpolating Catmull–Rom curve and a cached arc-length table. Travel is sampled by distance; heading follows the curve tangent, with a short initial turn from the preceding facing. Unwrapped angles preserve complete circles. Straight routes retain corners. End position and heading carry into following actions, including native animation and ladder approach.
- The gait follows distance traveled, with a gentle start/end fade. This is procedural locomotion, not planted-foot physics, terrain adaptation, or general pose blending. Curve interpolation may extend beyond the lines joining points; the visual map displays the sampled curve so creators can inspect it.
- The visual editor uses a top-down map with authored scene-object locations. Mouse/touch dragging and coordinate inputs provide equivalent point editing; the origin is fixed to the preceding sequence. Natural pace estimates duration at 1.1m/s walking or 2.6m/s running. Existing native travel is included when the browser computes the origin.
- Path changes are a single undoable scene edit. Revising one clip clones its motion when another clip uses it, preserving the other performance and the edited clip's ID. A changed scene or stale action prevents submission. Canceled drafts never mutate the project. The assistant's explicit `updateMotion` command intentionally revises all references to a custom action; built-in actions cannot be replaced.
- The assistant can create/revise paths directly or open the editor as its final workflow step. The labeled offline helper supports circle/square routes and opening/editing a character's path. Named route matching takes precedence over embedded words such as “walk”, so reusing “Circle walk” does not also append the generic Walk action.
- Routes remain level at their starting height. Automatic obstacle avoidance, moving-obstacle prediction, terrain/stair adaptation, and physical foot contact are outside this implementation. The map's prop markers are authoring references, not a collision simulation.

## Shared imported motions

- Selecting an imported action on another character adapts it automatically. The existing motion ID and original asset reference remain the source of truth; no lossy intermediate Euler-keyframe copy is stored. The action library distinguishes original playback from adaptation to the selected character, and the assistant can reuse the action by name.
- Transfer samples the original animation in a separate, hidden rig and converts its eleven recognized joints to anatomical world rotations relative to its calibrated neutral pose. The receiving body's neutral pose and bone axes reconstruct those rotations without changing skin inverse matrices. Original-source playback remains unchanged.
- Hip-to-ankle proportions scale translation between bodies. The initial source facing is normalized to the receiving character's facing. End travel and unwrapped final facing carry into later clips; full turns, reversed scrubbing, changed duration, and independent actors share the same sampler used by export. This does not add physical foot planting or general transition blending.
- Original motion sources are loaded independently of scene actors, cached within each viewport asset-loading lifecycle, and disposed on replacement/unmount. Readiness includes these sources before export. Hidden source rigs are never attached to the export scene. Removing the original character leaves its library asset intact; portable ZIPs retain that source file.
- Both bodies need the recognized humanoid hierarchy and uniform positive bind scale. Actions with animated non-root bone translations or skeleton scale remain on their original character with a staging message. Fingers, facial animation, morph targets, and arbitrary skeleton mappings are outside this transfer. This preserves usable original playback rather than claiming a universal result.
- The independent fixture is generated locally in Blender and uses namespaced humanoid bones with changed axes. It is not an Adobe asset and does not prove all Mixamo downloads compatible. Live provider and Unreal verification, automatic Mixamo operations, and broader asset-generation work remain open.

## Connected action sequences

- New chained clips use `transition: smooth`; new characters use `ending: hold`. Missing optional fields in old projects preserve Cut and Return to neutral behavior. The shared command schema, UI, offline helper, live assistant contract, and cast conversation staging support the same choices. Existing clip IDs and durations survive edits.
- A smooth transition blends from the previous final body pose into the incoming pose over at most 0.25 seconds, capped at half the incoming duration. World-space bone orientations and a hip correction prevent native parent travel being counted twice. Timeline travel and action duration are unchanged. Final hold retains the skeletal pose; it is not a general facial or morph-animation freeze.
- Targeted pick/sip/place/climb boundaries retain their own contact choreography. Their general transition controls are hidden. A carried prop still constrains the right hand after body blending. General collision solving, planted-foot transitions, and transitions into/out of arbitrary contacts remain outside this work.
- Native source clips now normalize initial facing and carry unwrapped yaw into later actions, matching adapted playback. This supersedes the earlier unfinished-facing note. The source file is unchanged; the scene's facing determines its initial orientation.
- Boundary samples are cached per rig and immutable scene/entity reference. Reverse scrubbing and edits use the same deterministic sampler as preview/export. Built-in bone translations/scales reset before each raw sample, preventing small offsets accumulating across repeated baking.
- Export freezes imported rig ancestor coordinate frames and transfers their motion to child tracks while preserving sampled world transforms and skin positions. Blender verification caught a curved interpolation artifact when native parent motion handed over to the studio root. Closely spaced keys were coalesced by Blender, so the final implementation fixes the coordinate frames themselves. Explicit clip-boundary samples also cover durations between the regular 24 fps samples.
- This adds supported skeletal transition blending; earlier notes that all transition blending was unfinished are superseded. It does not complete the remaining generation, live-provider, Mixamo automation, or Unreal requirements.

## Unreal project handoff

- Both Production package and Unreal project exports include a portable `SceneMaker.uproject`, required plugin declarations, startup configuration, and trusted Python adapter. The separate Unreal entry point and “Export Unreal” command make the destination discoverable without asking creators to run Python. The older `unreal_import.py` remains available for a deliberate import into an existing editor project.
- The project leaves engine association empty so the creator can choose their installed engine. The adapter targets the documented Unreal 5.6 API and rejects older versions before modifying a level. Unreal startup scripts run after the startup level loads; source data is resolved relative to the extracted project, so moving the entire folder remains supported.
- A SHA-256 manifest ties the setup to the exact scene JSON and baked GLB. The adapter validates those bytes and self-contained buffers/textures before modifying the world. This detects missing/mismatched export files; it is not a code-signing or authenticity claim.
- First import uses a fresh content namespace, creates a level, imports the hierarchy, checks the expected distinct rigs, adds basic editable key/fill lights, and saves assets and level. Completed imports reopen their recorded level without reimporting. Failed attempts retain their files; a retry gets a new namespace rather than overwriting partially imported or edited work.
- Imported render meshes may share a skeleton. Expected rig counts use connected joint ancestry, not the number of GLB skin entries. The actual browser fixture has seven skins and three rigs; treating skins as rigs incorrectly rejects a valid combined import.
- The report distinguishes imported/saved content from proven playback. It inventories animation assets and level sequences, warns when a source animation has no imported level sequence, and leaves `playbackVerified` false. No running Unreal Editor is available in this environment, so API contract tests and a valid package do not close that verification gap or the full original goal.

## Studio engineer: autonomous coding with no built-in limits

- Replace the read/edit-only coding loop with a full engineer agent: any file in the checkout, a host-environment shell, git commit and push, self-deploy into the running studio, HTTP, cross-provider `askModel`, bounded `delegate` sub-agents, and MCP servers from Connections. The old 24-step and 15-minute caps failed real tasks (the first attachment task died at step 24 with one file written); both are now opt-in environment variables and default to unlimited. Stop remains the human limit.
- Progress is a first-class contract: the agent must narrate one line before each batch of tool calls (`Assistant:` events), the service records step counts and last-activity time, and the Code panel shows elapsed time, step, the current line and a thinking-gap notice instead of a silent list.
- When the agent commits and pushes itself, the panel's sandbox checks are skipped: the agent is instructed to run `npm run check`, `npm test` and `npm run build` itself, and a pushed branch is already public. Panel-driven pushes keep the sandboxed checks and review hash.
- Self-deploy merges the task branch into the studio checkout's current branch, rebuilds, and restarts through `start.sh --restart`; a task marked `deployed` survives the restart as `pushed` rather than `failed`. It refuses when the studio checkout has uncommitted tracked changes.
- Every uncommitted change in the studio checkout is carried into the task checkout (previously only source-tree files), so the engineer works on what is actually running.
- Trade-off accepted explicitly: commands run with the host's environment and credentials. The checkout is isolated, but shell and HTTP are not sandboxed.

## Code panel as a conversation, and restart from the app

- A task is a conversation, not a one-shot job. The model history is saved per task (`messages.json`) after every step, so any reply continues with full context in the same checkout, including after a push or a studio restart. Replies used to be refused once a task was committed.
- The transcript is structured (`user`, `assistant`, `tool`, `status` entries) instead of a flat log. Tool calls are instrumented at the tool boundary, so MCP tools are covered too. Narration is captured with model middleware the moment a response arrives, so it appears above the tool calls it introduces.
- Messages sent while the engineer works use AI SDK steering and arrive at the next step boundary. A steered message is added to the saved history once delivered. Messages that miss the run, for example during checks, are queued and start the next turn.
- Long sessions trim older large tool outputs from the model context once the conversation passes about 400k characters, keeping the latest twelve results whole. The engineer can re-run a tool if it needs an old output again.
- A turn that changes nothing ends as **Done** (`idle`) rather than failing, so questions are first-class. Changed, unpushed work still goes through the sandboxed checks before the panel offers a push.
- Up to four tasks run in parallel. The list endpoint returns summaries only; the open task is fetched on its own, polled every second while anything runs.
- A run's final status is set only after its cleanup finishes, so a follow-up sent the moment a run fails cannot race the old run's teardown.
- Restart runs `npm run build` first and refuses to restart into a broken build. It only works when `start.sh` launched the service, which marks it with `SCENE_MAKER_LAUNCHER`, because only then is something present to bring the service back.
- Side panels wrap long text and code instead of scrolling sideways.

## Real 3D sets

- A library set can be a real glTF interior or exterior (`url`, optional `hdri` for its light) staged by a `set` block: home camera, bounds, spawn point and heading, an optional walkable polygon, a collision mode and lighting notes. A photographic set stays `hdri` without `url`. A creator's own GLB imported as a set gets the same block derived from its extent, so it opens with a sensible camera and collides like a library set.
- A 3D set brings its own floor: no studio slab is drawn or exported under it, unless the model has no floor under the spawn point (a facade or a prop used as a backdrop). Its home view replaces the studio's; a creator's fitted view moves nearer or around the cast when a wall blocks it. Exteriors orbit freely down to the floor; an interior (an Indoor set, or a creator's set with a ceiling over the cast) keeps the camera 30 cm inside its walls and under its ceiling, both measured from the home view's target when the set loads, through the orbit's own distance limit, so orbiting toward a wall brings the camera closer instead of through it.
- With an HDR a set is lit by it (optionally as the sky) at an exposure metered from the light on a level floor: the set pipeline's own measure when the set names none, and never so bright that a sunlit 80 % white floor passes 80 % display light. Without one the preset's sun lights it and a soft studio surround replaces the hemisphere fill, so metal and mirrors have something to reflect. Sets are shown clear unless they ask for fog. The sun's shadow box follows their bounds, around the spawn point within 30 m for a large exterior, with a 3 cm depth bias in any box.
- Collisions and routes read a per-mesh decision made once when the set loads. Shell meshes never block: tagged `sceneMaker.role` "shell"/"floor" in glTF extras, no higher than 5 cm (floor, rugs, thresholds), spanning 5 m both ways, or built around the room (a box that holds the spawn point and spans half the open floor one way). Furniture keeps its boxes; `collision: "none"` frees everything. Because walls may be walked through, the floor plan's edge (the walkable outline, or the bounds less a wall margin) joins the route footprints a body's radius outside it, so routes stay on the plan.
- New cast members stand on the spawn point, then on the nearest free spot outward in the set's frame: on the floor plan with a body's margin, clear of the loaded set's furniture, 0.75 m from the rest of the cast and not hidden behind them from the home camera. Adding a 3D set moves characters left off its floor plan (or at its edge) onto free spots in the same undoable step. Drops land on the set's furniture as on props, resting on its top, and something resting on the set's furniture is not counted as colliding with the furniture under it, whose box usually reaches higher (a bed's takes in its headboard). Only floor-level placements are kept on the floor plan.
- Large sets stream with a visible percentage, are never kept in the session download cache, and stop downloading once the creator leaves them; a set whose HDR fails still shows, lit by the studio. The shared glTF loader reads Draco, meshopt and KTX2 files; the Draco and Basis decoders are Apache-2.0 files that stay in the installed three.js package and are served from there under `/engine`, so the repository ships no copies. A library 3D set and its credit (licence link and a note that it was converted) travel with the production package, and a Credits dialog names every library artist, licence and source.
